# Syrmos 3.0.0 — implementation prompt and UI contract

Date: 2026-09-10. Baseline inspected: `9e717645` on `master`.
Status: **implementation specification**, not a statement that 3.0.0 has shipped.

Copy the following task into an implementation agent, or give it this file together with
[iPhone Duo and iPad readiness](../design/IPHONE-DUO-IPAD-READINESS.md).
The measurements below are product decisions for 3.0.0. They are not measurements of the
current app or of unreleased hardware.

## 1. The task

You are implementing Syrmos 3.0.0, “Journeys,” in this repository. Deliver a reliable
journey companion across native iOS, native Android, and the actual served web app.
Take a rider from choosing endpoints to comparing valid trips, following one, handling a
missed connection, and returning home. Preserve the current departure, map, network,
airport, fares, Ariadne, Ichnos, settings, widget, and watch capabilities.

Read this entire file, `docs/PRODUCT_PRINCIPLES.md`, `DESIGN_SYSTEM.md`,
`docs/plans/3.0-JOURNEYS.md`, the readiness document, and the relevant contribution rules.
Inspect the current source before editing: work may have landed after this audit.
This file resolves 3.0 layout and scope decisions where older design proposals conflict.
Existing correctness tests and truthful source labels remain constraints.

Work in reviewable phases on a branch. Implement and validate each vertical slice on all
three clients before declaring it complete. Record remaining work, test evidence, and
actual device coverage. Do not release to stores, tag a production release, or deploy a
public site as a side effect of implementing this prompt.

## 4. What “pixel precise” means here

All dimensions are logical units: **pt on iOS, dp for Android layout, sp for Android text,
CSS px on web**. Physical pixels equal logical units multiplied by the rendering scale.
Never put a screenshot's physical pixel width into app layout code.

Match the specified content rectangles, component anatomy, spacing, colors, ordering and
states. Capture separate baselines for each platform/OS/font/rendering scale. System
navigation, system fonts, keyboard and map tiles will differ. Their native sizing and
accessibility behavior take precedence over a forced imitation of another platform.

Measurements apply to default text size and the deterministic English fixture. Fixed
heights are **minimums** unless explicitly described as decorative geometry. Growing text
must increase height or change composition; never clip a destination or operational cue.

### 4.1 Coordinate system and breakpoints

Let `R` be the available app content rectangle **after** system bars, each individual safe
area inset, visible keyboard, and native navigation have consumed their space. Read the
current window/container, not the physical device screen. Do not subtract an inset twice.
On web, `R` excludes the navigation specified below. On iOS, native navigation placement
can change without a change in the device's marketing name.

| Available content width `W` | Mode | Content rule |
| --- | --- | --- |
| Under 600 | Compact | One column, 16 outer inset; card width `W − 32` |
| 600–839 | Medium | One readable column: `min(W − 48, 680)`, centered; 24 outer minimum |
| 840–1199 | Expanded | Planner/list 360 wide; 24 gap; map/detail takes remainder; 24 outer inset |
| 1200+ | Wide | Planner/list 400 wide; 24 gap; map/detail takes remainder; 32 outer inset; canvas max 1600 centered |

Expanded requires at least 360 units for the secondary pane; otherwise collapse to
Medium. Apply the rule independently to usable regions if the OS reports a dividing or
occluding fold region. A short window (`H < 480`) or accessibility text uses one scrolling
task column with optional map disclosure; it must not squeeze three panes above a keyboard.
These are Syrmos content breakpoints, not a redefinition of Apple's size classes.
Use size classes for native container behavior and measured space for content fit.

## 5. Navigation and platform composition

### iOS

3.0 native destinations, in order: **Home, Journeys, Explore, Map, More**. Move the current
Airport tab into a prominent airport shortcut on Home and a universal Departures entry in
More; preserve existing deep links to that function. Ariadne is a labelled toolbar action
and contextual “Ask about this” action. Do not float it at a guessed offset above tabs.

Keep native `TabView` and per-destination navigation stacks. In a regular roomy window,
use a native adaptable sidebar/tab presentation and Journey list/detail composition.
Native bars own their actual height/axis: do not force a 49pt bottom strip on iPad or Duo.
Selected tab, navigation path, picker query and journey draft belong to scene state, not
to disposable width-specific view branches. Present selection-dependent sheets with typed
selection state. Large sheets use native presentation and a readable form max width 560.

### Android

Same five native destinations and order. Compact navigation bar uses 80dp content height
plus navigation-system inset; five equal slots, 24dp icon, 12sp label. At window widths
600–839dp use an 80dp rail; at 840+ use a 240dp expanded drawer when it still leaves the
required content width, otherwise retain the rail. Content width rules apply **after** it.
Use the current Compose navigation stack; retain state with saveable state/persistent
session storage. Back closes picker/sheet first, then detail, then leaves the destination;
it does not end GO. Respect gesture-navigation, IME and cutout insets.

Use Android window size and posture APIs instead of manufacturer model checks. A separating
hinge must not contain a CTA or split a sentence. Google's adaptive window classes are the
platform basis; Syrmos's pane minimums additionally decide whether content fits.
[Android window size classes](https://developer.android.com/develop/adaptive-apps/guides/use-window-size-classes).

### Web

Retain URLs and workspace meanings: **Now, Plan, Explore, Departures, Tickets**; More is a
utility menu; Map remains the shared canvas/action. This preserves existing web links while
native Journeys maps to Plan. Do not create a sixth primary compact destination for GO.

Viewport <600px: bottom bar 64px + `env(safe-area-inset-bottom)`, five equal slots, 20px icon,
11px label; header 56px. 600–959px: 80px left rail, header 64px. >=960px: 240px left
navigation, header 64px. Content starts after these regions. Main desktop grid uses the
remaining width, so a 1440px browser with a 240px rail has 1200px of content available.
Below 600px all primary destinations remain reachable; the existing hidden-nav rule must
not survive without a replacement. Remove the user-agent app-blocking page.

Use semantic links/buttons/forms; `aria-current` for workspace selection, a skip link,
visible focus and a labelled map alternative. No hover-only actions. Keyboard: Tab follows
visual reading order, Enter activates, Escape dismisses the top non-destructive overlay and
returns focus to its trigger. Browser Back/Forward restores route and selection.

Use dynamic viewport sizing with a fallback; keep input and submit reachable when the
keyboard changes the visual viewport. Listen only where needed, cleaning up observers.
The visual viewport can shrink independently of the layout viewport.
[MDN VisualViewport](https://developer.mozilla.org/en-US/docs/Web/API/VisualViewport).

Preserve `docs/adr/0001-web-url-model.md`: static entry directories and query parameters,
root-absolute assets, no `<base>` element. Route drafts use `/plan/?from=<id>&to=<id>`;
extend validated parameters for date/mode/preferences. Do not put precise GPS, “Home” labels,
notification tokens or active session secrets in share URLs. Shared trips are planning
requests recomputed at open time, with the date explicitly shown.

## 6. Screen-by-screen implementation

All dimensions inherit sections 4–5. Render the same data states on every platform.
Expanded layouts retain logical reading order: inputs → options → selected detail → map.
Screen IDs below are stable screenshot/automation identifiers.

### S01 — Home / Now

Compact order: header → active-trip card OR next-departure hero → “Plan a journey” → saved
journeys → airport shortcut → relevant disruption → existing supporting modules.
Use only one dominant countdown. An active GO card replaces the departure hero.

Hero: radius 24, padding 24, min-height 204; context label 16 line box, gap 8, destination
22/28, gap 12, countdown 44/48, gap 8, source row 13/16. Action row follows with gap 16.
“Plan a journey” is a 56-min-height field-like button with 20 icon, 12 gap, title and chevron.
Saved rows are 72 minimum, two text lines and trailing 44/48 menu; show up to three then
“See all.” No automatic carousel. In Expanded put this column beside a full-height map;
supporting modules follow under the hero column rather than overlapping map controls.

Tap resume opens the current GO session, not a freshly planned copy. No nearby station:
“Choose a station” action. No location permission: station search remains first-class.

### S02 — Journey / Plan draft

Header title “Plan a journey”; trailing Saved action. Endpoint card: radius 16, padding 16.
Each endpoint row min-height 64 with 13/16 “From” or “To” label above 17/22 station text,
8 gap; 1-unit divider between rows. Leading icons are 20 within 24 width, 12 gap to text.
Swap is a separate 44/48 button below the endpoint pair, right aligned; it never covers text.
Selecting From/To opens S03. Default From is the last explicit station; GPS is suggested
only if allowed and sufficiently recent. Do not silently change an entered origin.

Below card: gap 16, travel-time control min-height 48 (Leave now / Depart at / Arrive by),
gap 12, preference chips Fastest / Fewer changes / Less walking, gap 16, 52-high “Find routes.”
Accessibility preference is a labelled separate control with an “Unknown information”
explanation; do not imply verified step-free access from the presence of a switch.
Results replace the lower part, preserving the draft at top. Expanded puts draft/options
in the first pane and selected route/map in the second.

Identical endpoints: inline body message “Choose a different destination,” focus To;
search not submitted. Missing endpoint: label the missing field; do not erase the other.
Date picker uses Athens service date and explicitly shows it in the selected locale.

### S03 — Station selector

Compact: full-height native sheet/page, or web dialog/page occupying the visible viewport.
Header min-height 56: Back/Close 44/48, title “Choose origin” or “Choose destination.”
Search field min-height 52, radius 12, 16 side margins; 20 search icon and separate clear
button. Gap 16, Recent section, then matching stations. Row min-height 72: primary name
17/22, secondary region/line 13/16, 8 gap; leading station icon 24, trailing selection check.
Search is accent-insensitive for Greek/Latin queries, debounced 200ms, and locally usable.

Web desktop dialog max-width 560, max-height `min(720, visibleHeight−48)`, padding 24;
results alone scroll. Native uses native sheet sizing with the same readable content cap.
No results: 20px search icon, title “No matching stations,” entered query, action Clear.
Rows must distinguish identically named stations in different regions. Cancel leaves the
draft unchanged; selection commits exactly one endpoint and returns focus to its trigger.

### S04 — Route results

Summary: “3 routes” or actual count, travel date/time, source row; never render filler
options to reach three. First result selected, badge “Fastest” only if that ranking is true.
Option card: min-height 184, padding 16, 16 radius, 12 vertical gap. Selected outline 2 brand;
unselected outline 1. Entire card selects; Start belongs to S05 and is not an ambiguous

Anatomy: label row 16; gap 8; clock range 22/28 left and duration 17/22 right; gap 12;

min-height 32. Wrap route chains onto additional lines. Use tabular clocks; prepend `~` or

Footer: “Times use Athens time” only when device timezone differs; data explanation always

### S05 — Selected journey detail

Compact: title and Save/Share utility actions, summary card, itinerary timeline, source
explanation, bottom action region. Action region has 16 padding, top outline 1, primary
52-high “Start journey”; it participates in safe area/IME layout and never covers the last row.

Summary: duration 22/28; departure/arrival 17/22; confidence block below with 12 gap.

The current instruction dominates. Compact: header “Journey in progress” + End utility;
instruction hero, confidence/freshness, route progress, next action, expandable remaining
stops. Map is optional below, not required to understand the next step. Expanded keeps
instruction/timeline at left and map at right; no duplicates of the main countdown.

Hero min-height 220, padding 24, radius 24. Top state label 13/16; gap 12; instruction

Bottom region: primary 52 action, secondary 44/48 manual correction, 12 gap.

| --- | --- | --- | --- |
| Ready to board | “Board M2 toward …” | “I'm on board” | View departure / End |

### S07 — Connection risk and alternatives

Inline warning inserted directly below the current GO instruction; min-height 88, padding
16, warning container, icon 20 + 12 gap, title 17/22, explanation 15/20. Example:

## 7. Data and journey behavior contract

### 7.1 Extend models rather than duplicating business logic in views

Add versioned language-neutral JSON fixtures alongside `fixtures/go-guidance/cases.json`.
Use equivalent typed Swift/Kotlin/JS models. Proposed contract (names may map to existing
types, semantics must stay stable):

```text
JourneyRequest: schemaVersion, fromStationId, toStationId,
  timeMode(now|departAt|arriveBy), requestedInstant, serviceTimeZone(Europe/Athens),
  ranking(fastest|fewestChanges|leastWalking), accessibilityPreference
JourneyOption: id, requestId, legs[], departureInstant?, arrivalInstant?,
  durationSeconds?, transferCount, walkingSeconds?, sourceSummary, feasibility
Leg: id, kind(ride|walk|transfer), fromId, toId, lineId?, directionId?, tripId?,
  orderedStopIds[], departureInstant?, arrivalInstant?, serviceDate,
  timingKind(live|scheduled|estimated|unknown), uncertaintySeconds?,
  transferMinimumSeconds?, accessibility(verified|unavailable|unknown), sourceRef
SourceRef: sourceId, observedAt?, fetchedAt?, validUntil?, snapshotVersion,
  statusCoverage, scheduleCoverage
Feasibility: status(comfortable|tight|missed|unknown), minimumMarginSeconds?,
  explanationCode, limitingLegId?
SavedJourney: id, label?, fromId, toId, preferences, createdAt, schemaVersion
ActiveJourney: id, revision, itinerarySnapshot, phase, legId, confirmedStopId?,
  progressSource(manual|gps|matchedVehicle|scheduleEstimate), progressObservedAt?,
  startedAt, updatedAt, alertedEventIds[], alertPreferences, schemaVersion
```

Null means unknown, never zero. IDs are stable across recomputation where the trip really
is the same; matching by list index or station display name is forbidden. Persist with an
atomic, versioned migration path. Corrupt/unsupported state opens a recovery UI.

### 7.2 Routing and time

All schedule evaluation uses `Europe/Athens`; store absolute instants and the operator's
service date. Use the repository's Athens-time helpers. Do not assume every date is 24h.
Explicitly test DST, midnight crossings, service hours beyond 24:00, holidays and Saturday
overnight service. Never derive a production timetable from an illustrative screenshot.

Search state includes station, line/direction/trip context and time, so transfer cost cannot
be skipped by collapsing every line at an interchange into one node. Traverse the actual
ordered stops. Retain line-status exclusions and apply section/time-bound disruptions when
available. Unknown disruption coverage is disclosed, not converted to an open line.

Rank by requested objective, then arrival, changes, walking, stable ID. Deduplicate identical
leg sequences. Show at most three materially distinct options. Arrive-by uses a backward
time-aware search or equivalent verified method; it does not subtract a static duration
from the requested arrival. Last-connection-home searches the whole chain to the chosen
destination across the relevant service boundary. If walking data is unavailable, “Less
walking” is unavailable with an explanation; do not invent exact meters.

### 7.3 Timing margin and truthfulness

For transfer `i`, compute:
`margin = nextDeparture − previousArrival − transferMinimum − uncertaintyAllowance`.
All terms are seconds. A required unknown term makes feasibility unknown. For the initial
release use configurable, fixture-covered thresholds: margin <0 missed; 0–179 tight;
>=180 comfortable. The journey takes the worst valid transfer state. A closure overrides
it to unusable. Source uncertainty remains visible even for a comfortable scheduled plan.

UI says “5 min margin · scheduled,” not a fabricated 96% success score. For a direct trip,
evaluate ability to reach boarding only if access time is known; otherwise show direct/
schedule status, not a transfer confidence calculation. Explain any default transfer buffer
as an estimate, and do not equate straight-line GPS distance with walkable access.

Live freshness default proposal: observed fix <=60 seconds and within provider validity;
GPS fix <=30 seconds with acceptable accuracy and plausible route/direction match. Put
thresholds in policy/fixtures, not view code. Historical cache does not extend validity.
Schedule availability and disruption validity use their own coverage timestamps, not the
live-position TTL. A 1-second client simulation is still Estimated.

### 7.4 GO persistence, sensors and alerts

State transitions are explicit and idempotent. Replaying the same fix/event must not
advance twice or send a second alert. Event IDs include session, itinerary revision, leg
and cue type; save deduplication state. Manual corrections can move backward intentionally;
automatic updates cannot undo a confirmed stop or jump across a transfer without evidence.

Map-matching needs accuracy, timestamp, direction and route plausibility checks. GPS near
an interchange cannot by itself prove the rider changed trains. Cold resume shows last
confirmed progress before processing new observations. Freeze the itinerary snapshot during
active guidance; new service data creates a warning/revision proposal.

**Offline guidance is available; an accurate offline get-off alert is not guaranteed.**
With no location/vehicle evidence, offer manual progress and clearly labelled scheduled
reminders. Suspended/background apps and closed browser tabs cannot be treated as continuously
running trackers. Do not add background-location permissions without implementing and
validating their actual lifecycle. The existing iOS background mode is `fetch`, not location.

One global active journey may be shared across scenes, but draft/navigation/map selection
are scene-local. Two windows must not schedule two alerts. Native host recovery must restore
session state, while preserving the documented iOS rendering workaround until its underlying
bug has a verified replacement. See the readiness document's remaining lifecycle work.

## 8. Glance surfaces and permission behavior

iOS: reuse `SyrmosWidget`/ActivityKit infrastructure for an explicitly started journey.
Show current action, destination, next meaningful time and freshness in each available
family. Expandable views may add transfer context; no tiny timetable. Gate APIs by runtime
and build SDK, update on meaningful events, end/cancel cleanly, show stale content honestly.
Live Activities do not grant continuous background execution. Push-to-start is a separate
backend/token/consent deliverable; do not call it complete after building a local activity.

Android: use existing notification infrastructure, with supported ongoing notification
fallbacks. Where supported, use system `ProgressStyle`, promotion request/capability checks,
and the required manifest declaration. A Live Update is for an ongoing user-initiated trip;
promotion is subject to system/user decisions. Retain a standard notification if promotion
is unavailable. Do not use custom notification layouts while claiming promoted eligibility.
[Android Live Updates](https://developer.android.com/develop/ui/views/notifications/live-update).

Web: preserve active trip locally and foreground cues; resume visibly on return. Service
worker caching and PWA installation do not provide continuous location or guaranteed timed
alerts after closing the browser. Keep Web Push out of the core acceptance criteria.

Notifications denial never blocks planning, saving or manual GO. No permission prompt on
first launch solely to make the new feature possible; ask at its point of use.

## 10. Verification and acceptance

### Deterministic behavior fixtures

At minimum cover: direct trip; single/multiple transfers; same endpoints; duplicate station
names across regions; inaccessible/unknown interchange; suspended line; partial closure;
stale status; no timetable coverage; arrive-by just before/after last arrival; overnight;
DST both directions; Saturday 24-hour rules; missed/179s/180s margin; unknown uncertainty;
duplicate GPS event; bad accuracy; wrong-direction fix; repeated interchange; manual
correction; relaunch; data migration; route replacement; two observers of one active trip.

Keep expected data language-neutral. Add `fixtures/journeys/` for planning, state and

Extend the existing GO fixture contract without silently reinterpreting old cases.

### Definition of done

- A rider chooses real endpoints and completes the resulting trip on each platform.
- Route times, status exclusions, confidence and GO transitions agree on shared fixtures.
- No production entry starts a fixed demonstration journey.
- Offline/manual mode, denied permissions, restart and missed connections have useful UI.
- iPad resize, compact/expanded transitions and accessible text preserve the active task.
- Android large windows and mobile/tablet browsers have complete navigation.
- Screens match their documented geometry and platform-specific baseline evidence.
- The final report separates implemented, tested, deferred and SDK/device-blocked work.
- Duo optimization is claimed only after the dedicated readiness gates pass.

# 3.0.0 Finding 7 - journey ranking decision

Status: **decided and implemented** (product owner accepted option 2 in-session,
2026-09-16). This record separates the contract violation that was repaired from
the product policy that was then chosen, per finding 7.

## 1. The contract violation (repaired independently of the policy)

Section 7.2 specifies the ranking chain: requested objective, then arrival, then
changes, then walking, then a stable id. The shared Kotlin `JourneyRanker` and web
`web-journey-ranker.js` implement that chain. iOS `JourneyPlanAdapter.planAll`
sorted candidates by `durationSeconds` alone, dropping every tie-break, so its
order could diverge from the other clients on equal durations.

Repair: iOS now orders through `recommendedSortKey`, a deterministic total
ordering that applies the same objective chain (duration, arrival, changes, stable
id from the line chain). Unknown arrival stays unknown and sorts last among ties,
never a fabricated 0.

## 2. The audited S04 case

At the pinned 08:42 the S04 list read (rounded labels):

| # | Route | Rounded | Changes | Feasibility |
|---|-------|---------|---------|-------------|
| 1 | M1 → A1 | ~48 min | 1 change | Tight (selected) |
| 2 | A1 (direct) | ~48 min | 0 changes | Comfortable |
| 3 | M1 → A2 | ~56 min | 1 change | Comfortable |

Two cards showing "~48 min" do not prove equal journeys: the rounded label hid the
real unrounded difference and, more importantly, feasibility was not a ranking
input at all, so a tight route led a comfortable one. Feasibility thresholds are
unchanged: negative margin is missed, 0 to 179 seconds tight, 180+ comfortable, and
a required missing term is unknown. A direct ride's "comfortable" reflects that it
has no connection to miss, not a claim about boarding access time.

## 3. The two policy options presented

1. **Keep objective-first.** Fastest ranks first even when tight; its risk and the
   real time trade-off are shown, and feasibility becomes a visible badge but not
   the primary sort key. Equal metrics use the existing deterministic tie-breaks.
2. **Prefer comfortable journeys (recommended).** The default recommendation
   prioritizes known-comfortable options over genuinely faster but tight/unknown
   ones. Honest objective labels are preserved: a slower recommendation is never
   labelled "Fastest". Objective-first stays available as an explicit mode.

## 4. Decision

The product owner chose **option 2** and accepted its time trade-off (in-session,
2026-09-16). Rationale: the app's job is to get the rider there reliably; a route
they are likely to miss should not be the headline recommendation.

## 5. The implemented rule

A new default ranking `RECOMMENDED` (wire name `recommended`) with a deterministic
total ordering:

1. **Feasibility class** - comfortable (0) < tight (1) < unknown (2) < missed (3).
2. **Objective** within a class - duration ascending (fastest), then arrival, then
   change count, then walking, then stable id.

Badge: the top option is badged `recommended` only when it is genuinely feasible;
if every option is missed there is no recommendation and the top carries no badge.
A missed or closed journey is therefore never an actionable recommendation.

### Extra journey time accepted

No invented minute penalty or cutoff. The extra time a comfortable option may cost
over a faster tight one is **bounded by candidate generation**: the planner returns
at most three materially-distinct routes for the same origin/destination, so the
comfortable recommendation is always drawn from realistic alternatives for that
exact trip, not an unbounded search.

### Unknown and missed handling

- Unknown feasibility sorts below tight: a direct ride without known boarding
  access time is not evidence of a comfortable connection, so it does not jump
  ahead of a connection we can actually vouch for.
- Missed/closed sorts last and is never badged.
- Unknown objective metrics (null duration/walking/arrival) keep the documented
  nulls-last fallback and never become zero.

## 6. Where it is implemented

- Shared: `core/domain/.../journey/JourneyRanker.kt` (`Ranking.RECOMMENDED`,
  `feasibilityClass`, comparator + badge), `core/model/.../journey/JourneyModels.kt`
  (enum case).
- Web: `web-journey-ranker.js` (mirror), default request `ranking: "recommended"`
  in `web-map.js` (active plan and saved-journey preference).
- Android: `PlanScreenRoute.kt` default `Ranking.RECOMMENDED` for the active plan
  and saved-journey preference.
- iOS: `PlanFlow.swift` `JourneyPlanAdapter.recommendedSortKey` used by `planAll`.

## 7. Tests

- `fixtures/journeys/ranking.json` extended with `recommended_*` cases: comfortable
  over faster tight (S04 shape), missed never leads, all-missed no badge, tight over
  unknown.
- Kotlin `JourneyRankerTest` and web `journey-ranking.test.js` drive those cases.
- iOS `JourneyRankingOrderTests` mirrors them against `recommendedSortKey`.

Objective-first (`FASTEST`, `FEWEST_CHANGES`, `LEAST_WALKING`) behaviour and its
existing golden cases are unchanged and still covered.
